# find_ocx documentation: information architecture plan

Source of truth: `docs/discovery/use-cases.yaml` (tasks, needs, inventory, `ia_plan`). Tables below are rendered from it. Nothing here edits a page; the delete list and the declaration patch wait for the maintainer.

- Product shape `library`, wrapper over a CLI. Ranking signal `friction-log-severity`: no issues, four pull requests, no telemetry, no search logs, so no higher-priority signal exists. Rank = blockers, then majors, from each task's friction log; unlogged tasks rank below every logged one. No percentage or count of people appears anywhere.
- Six tasks were friction-logged against v0.3.0 (persona runs, verbatim output). Nine were not; T12 and T13 cannot be logged until P2 merges.
- Tier is dependency order, not rank. The entry task is T02 (rank 2). T01 (rank 1) needs a provisioned package and a pin first.
- Decisions carried in: Sphinx retired, Markdown in `site/pages` is the source, reference generated from `#[=[.rst:` blocks, casts regenerated at site build.

First-steps contract for T02: one precondition sentence above the first fence (CMake plus network access or a mirror; no `ocx` install is needed once the lock question O1 is settled), then at most 4 fenced blocks from the heading that introduces the runnable snippet to the first block that shows `jq` output (count fences, not list items). `tutorial` type is kept because the reader assembles four interacting parts (vendored module, tool list plus lock, `ocx_project` exports, a build target); the landing page carries the quick start for readers who need less.

## Open questions and plan deltas

- **O1.** The tutorial and quick start tell the reader to run `ocx lock` with a CLI installed first. That is circular for a blocked-network reader (friction T03 item 7) and caused the version-skew blocker (T02 item 1). I4/I1 should decide whether a first configure can write the lock with the bootstrapped CLI. T02's page text depends on the answer.
- **O2.** `doc_tier` removal on non-required types is a proposal; the checker tolerates a tier on any type, so keeping it is also valid.
- **Delta 1.** Plan D3 lists "superbuilds and nested OCX_* env" as a how-to. Evidence is one unlogged error (T08, rank 8), so it becomes a section of `troubleshooting/configure-errors.md`.
- **Delta 2.** Added beyond the plan's D3 list: `guides/index.md` (the everyday hub the nav break needs), `guides/use-system-ocx.md` (split from find-package, T09), `guides/policy-and-config.md` (T13, split from the mirror how-to), `concepts/env-and-config.md` and `troubleshooting/exit-codes.md` (both in the plan, as pages). CA bundle and managed config stay in the mirror page's `must_cover`.
- **Delta 3.** Casts: the plan's six (one exists) plus three proposed (`stale-lock`, `find-program`, `foreign-paths`); the proposed ones show friction-log failures that the module's own message cannot fix.
- **Delta 4.** The reference examples group (three pages) is on the delete list; the plan did not mention it.
- Items under `fixed_by_plan` in the YAML (version skew, newline truncation, `ocx run` text) are expected to vanish with P2. If a post-merge re-run of the six personas still hits them, they become `must_cover`.
